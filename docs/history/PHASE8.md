# Phase 8 — gated Dev images, migration and application delivery

**Status as of 2026-10-19:** The owner reports Terraform, the `helpdeskcloud-dev-gke` Autopilot cluster, `helpdesk-dev` namespace, bootstrap ServiceAccounts, SecretProviderClasses, SQL ConfigMap, restricted PostgreSQL application user and Secret Manager versions are in place. This PR does not read cloud state or secret payloads. The schema migration has not been run, supporting images have not been published, and application delivery remains disabled. No public endpoint is introduced.

This phase prepares three separate release checkpoints:

1. `supporting-images-ci.yml` builds and scans the Cloud SQL Auth Proxy and custom PostgreSQL migration client on PRs. A trusted `dev` run creates and verifies GitHub SLSA provenance for the exact image archives. Publication is a manual dispatch, gated by a dedicated GitHub Environment, a disabled-by-default repository variable and a separate WIF identity.
2. `dev-db-migration.yml` is manual-only and has separately selected diagnostic and migration modes. Diagnostic mode requires `DIAGNOSE helpdesk-dev-gke` and uses the same protected `dev-db-migration` Environment, WIF provider, runner service account and DNS endpoint. It introspects the exact bearer token from the action-generated kubeconfig through a POST to Google's tokeninfo endpoint, reporting only whether the token email and required OAuth scopes match. It separately exercises a kubeconfig generated with Google's documented [`gcloud container clusters get-credentials --dns-endpoint`](https://docs.cloud.google.com/sdk/gcloud/reference/container/clusters/get-credentials) and supported [GKE exec-plugin configuration](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/api-server-authentication). Both checks report sanitized results, and a failed connectivity or identity/RBAC check fails the diagnostic job after both read-only paths are attempted. Neither path writes Kubernetes resources or runs SQL. It does not request the cluster-scoped Namespace object because the runner's Kubernetes Role is intentionally limited to `helpdesk-dev`. Migration mode retains the exact typed confirmation `RUN helpdesk-dev-schema-001`, the disabled-by-default migration variable, rendering of only the existing chart's one-time Job, and the separate Environment approval. It uses the same supported DNS-endpoint exec-plugin kubeconfig and refuses to replace an existing Job.
3. `app-dev-delivery.yml` remains the existing application release path. Its `dev-app-publish` and `dev-app-deploy` approval gates and internal ClusterIP checks are preserved. It never runs the database migration.

No workflow in this PR was dispatched. CI has no Google credentials. Publishing, migration, application deployment and infrastructure changes require the reviews below.

The publisher downloads and verifies the same archives before requesting Google credentials.

It reads each resulting registry digest and prints the full image reference and SHA-256 digest into the run summary. If the first push succeeds and the second fails, keep the first image as an immutable artifact, review the failed run, then use a new workflow attempt; do not move or delete the tag.

### Interpreting the read-only GKE diagnostic

The diagnostic checks the ADC impersonation target and introspects the exact token from either credential path: the static token in the action-generated kubeconfig, or the credential response from the verified `gke-gcloud-auth-plugin` command. Each token is sent only in the body of an HTTPS POST to Google's tokeninfo endpoint. For plugin mode, the script creates a mode-restricted temporary kubeconfig containing that exact token, uses it for the read-only Kubernetes probes, then removes it; neither the token, kubeconfig contents nor tokeninfo response are printed. `kubectl auth whoami` reports the server-observed identity only when the Kubernetes API responds. The `roles/container.clusterViewer` binding covers cluster lookup and DNS-endpoint connection, while Kubernetes object operations are authorized separately by the namespace Role. The diagnostic therefore checks namespace access through namespaced bootstrap-object reads and `kubectl auth can-i` probes only.

An HTML 403 from the `*.gke.goog` endpoint is reported as a DNS-front-end denial, distinct from a Kubernetes `Status` Forbidden response. It does not by itself identify IAM, VPC Service Controls, or another frontend restriction. `allowExternalTraffic` confirms endpoint reachability configuration, not that a caller passes every authorization or perimeter check. The latest diagnostic confirmed that the previous `use_auth_provider: true` path generated the legacy `auth-provider: gcp` kubeconfig mode, while the supported path is a `gcloud`-generated exec-plugin kubeconfig; the exact plugin stderr was suppressed, so the legacy configuration is the evidenced defect but cannot be claimed as the only cause of the separate short-token 403. The token comparison now proves the bearer identity and scope instead of inferring them from the ADC impersonation URL. No IAM or Kubernetes RBAC change is justified by the current evidence. If the corrected diagnostic still receives the DNS-front-end 403, correlate the sanitized result's time and actual token identity with the per-cluster IAM condition evaluation and any available VPC Service Controls identifier before changing access policy.

## Delivery and rollback boundary

The normal application workflow consumes the application digest produced by its own reviewed package job and the approved `DEV_PROXY_IMAGE_DIGEST`. It deploys the existing Helm chart with `values-dev.yaml` plus `values-dev-delivery.yaml`, which disables migration and bootstrap, pins both images by digest, keeps two replicas and a ClusterIP Service, and verifies health over a localhost-only port-forward. It never creates the migration Job. The migration workflow uses the same chart but renders only `templates/migration-job.yaml`, with `application.enabled=false` and `migration.enabled=true`.

For an application-only fault, inspect Helm history and use the existing owner-approved rollback process. Helm rollback does not reverse SQL schema changes or Terraform. Never rerun the fixed migration Job to suppress an error; review database state and prepare a separately reviewed, versioned migration. Stage and Production resources, identities, registries, Environment approvals and workflows remain out of scope.

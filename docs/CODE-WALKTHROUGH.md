# Code walkthrough for the capstone

This guide points to representative code rather than repeating entire files. Paths are relative to the App repository unless marked Infra. Each trainer answer is a concise explanation of the design.

## Cloud network and private database — Infra

- terraform/modules/network/main.tf creates the VPC, subnet, GKE secondary ranges and private services access range. The module keeps network resources reusable while preserving the established Terraform state addresses. **Trainer answer:** “I put the reusable network in a module so the project has one clear VPC boundary and the cluster and database consume the same configured ranges.” If the network or PSA connection is missing, private Cloud SQL and GKE cannot connect as designed.
- terraform/cloud-sql.tf sets ipv4_enabled to false, selects the existing VPC and enables deletion protection. **Trainer answer:** “PostgreSQL has no public IPv4; the app connects through its in-Pod proxy over the private network. Deletion protection guards the database and its persisted tickets.” A broken private route or proxy identity fails readiness rather than exposing the database.
- terraform/gke.tf depends on node runtime and image-pull grants and enables Autopilot and Workload Identity. **Trainer answer:** “The node identity is ready before cluster creation, and Pods get their own Google identity through Workload Identity.” Without the dependency, a fresh cluster could be created before its node permissions are in place.
- terraform/gke-iam.tf separates node, application and migration identities. Its Workload Identity members depend on cluster creation because the cluster creates the identity pool. **Trainer answer:** “The running app gets only Cloud SQL Client, while the one-time migration has a separate identity.” A missing binding prevents the relevant Pod from authenticating to Cloud SQL.

## State and protected infrastructure workflow — Infra

- terraform/environments/dev.gcs.tfbackend selects bucket helpdeskcloud-tfstate-511905 and prefix helpdeskcloud/dev; HTTPS roots have their own prefixes. **Trainer answer:** “GCS keeps remote state and locking, while prefixes isolate the three root histories. The names are stable because state maps code to existing resources.” A wrong prefix can make Terraform believe resources are new.
- .github/workflows/terraform-dev-plan.yml authenticates with OIDC, initializes the existing backend and produces a read-only plan passed through strict drift checks. **Trainer answer:** “The Plan workflow reports what Terraform would do and never applies it.”
- .github/workflows/terraform-dev-apply.yml makes a fresh plan, checks its safety and drift fingerprint, then waits on the protected dev-network-apply Environment before Apply and verification. OIDC supplies short-lived credentials instead of a service-account key. **Trainer answer:** “Approval applies to a current, validated plan, so stale plans and unexpected replacements are rejected.” If approval, branch policy or validation fails, Apply does not proceed.
- The Infra project identity intentionally retains roles/iap.admin by owner direction. The exact single-user access grant is separate in terraform/https-access/iam.tf as google_iap_web_backend_service_iam_member.helpdesk_user, using roles/iap.httpsResourceAccessor. **Trainer answer:** “The project administrator identity is an explicit owner-approved exception; end-user access is still granted to one account on the exact backend.”

## Application, image and database

- src/HelpDeskCloud/Program.cs fails startup if enabled IAP lacks the expected audience or approved email, loads the database connection from a mounted secret file in GKE, and registers assertion middleware before API routes. **Trainer answer:** “The edge is the first gate and the app is the second; missing IAP settings make a deployment fail closed.” If a required option or secret mount is missing, startup fails rather than running without the required control.
- src/HelpDeskCloud/Security/IapAssertionValidator.cs validates Google's signed IAP JWT, issuer, audience and user email. The active backend's numeric ID is 4800183520372038985. **Trainer answer:** “A request header alone is not identity; we verify Google's signature and the claims that bind the assertion to this backend and approved account.” Invalid or missing assertions receive HTTP 401.
- helm/helpdesk/templates/deployment.yaml defines two replicas, readiness/liveness probes, a non-root app container and Cloud SQL Auth Proxy sidecar. The proxy uses private IP and binds its database listener to Pod loopback. **Trainer answer:** “Two replicas provide availability during a rollout, and the sidecar gives the app local authenticated database connectivity without a public database endpoint.” If either container is unready, Kubernetes removes that Pod from service.
- helm/helpdesk/templates/service.yaml keeps the app behind an internal ClusterIP. **Trainer answer:** “The public entry point is the Gateway; the application Service is private to the cluster.”
- database/init.sql is the canonical initial schema for local Compose; helm/helpdesk/files/001_init.sql is the required mirror packaged by the manual migration Job. `.github/scripts/check-schema-parity.py` and `tests/test_schema_parity.py` compare the files byte-for-byte offline. The schema contents and table structure were not changed. **Trainer answer:** “The local rebuild has one canonical schema, and CI catches a stale Helm copy without adding a migration framework.”
- `.github/scripts/verify-dotnet.sh` holds the restore, build and test commands shared by app-ci.yml and the protected package job in app-dev-delivery.yml. **Trainer answer:** “CI and release packaging validate the same source while keeping validation separate from the approval that can publish or deploy.”
- `.github/workflows/dev-db-migration.yml` remains manual-only, uses the distinct `dev-db-migration` Environment and the dedicated migration service account. Diagnostic mode runs `.github/scripts/diagnose-dev-migration-connectivity.py` read-only; migration mode requires a separate opt-in, exact confirmation and a one-time Job that refuses to replace an existing Job. **Trainer answer:** “Database migration credentials are separate from the runtime app identity, and connectivity diagnostics do not run SQL.”

## HTTPS, Gateway and IAP

- helm/https-edge-access/templates/edge.yaml creates a port-443 Gateway that references the existing certificate map and static address, an HTTPRoute to the internal Service, a Google TLS policy, an IAP-enabled backend policy and a health-check policy. **Trainer answer:** “The separate edge release owns public HTTPS and access policy; it routes to the internal app Service and has no public port 80.” If controller conditions or policy attachment fail, the delivery pipeline stops.
- k8s/dev-delivery-rbac.yaml grants namespace-scoped permission to reconcile the Gateway and GKE policy resources. k8s/dev-migration-runner-rbac.yaml separately authorizes the database migration. **Trainer answer:** “Each workflow identity receives only the Kubernetes resources needed for its operation; neither uses cluster-admin.” Missing RBAC blocks the workflow before it changes a release.
- .github/workflows/app-dev-delivery.yml verifies the protected Environment and exact artifact, publishes by immutable digest, deploys under separate approval, checks replica health, waits for Gateway conditions and probes all app routes over normal TLS. Anonymous responses must prove the expected Google IAP flow and OAuth client. **Trainer answer:** “Controller readiness and public load-balancer readiness are different, so the workflow checks both and retries within a fixed deadline.” If an endpoint is public, TLS fails or IAP is not attached, delivery fails with a diagnostic summary.
- .github/scripts/check-https-edge.py validates rendered edge resources and checks that live anonymous responses carry X-Goog-IAP-Generated-Response and target the expected Google OAuth client. **Trainer answer:** “We do not accept an arbitrary redirect as evidence that IAP is protecting the route.”

## Promotion model

Feature PRs run App CI without cloud credentials. A merge to protected dev may enter the protected publishing and deployment Environments. Stage and Prod branches are prepared for future promotion and are not represented as deployed environments.
